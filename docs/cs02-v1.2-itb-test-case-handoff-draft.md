## Shared assertions to add to presentation cases

1. **Identity and retrieval:** strict CS-02 uses `x509_hash:` plus unpadded base64url SHA-256 of DER `x5c[0]`, without a `sha-256:` infix. Validate JAR ES256/P-256 signature and independently compare the leaf hash. Invocation `client_id`, retrieved signed JAR, and session identity must agree. GET and POST retrieval must retain state, nonce, DCQL, and mode; POST must echo `wallet_nonce` when supplied.
2. **Response encryption:** default and explicit strict cases use `direct_post.jwt`. The wallet POST is form-urlencoded with a compact JWE in `response`. Decrypted plaintext is the top-level authorization-response JSON (`vp_token`, applicable `state`), not a signed JWT inside the JWE. Preserve DCQL arrays by credential-query ID and existing nonce, audience, holder-binding, transaction, and mdoc checks.
3. **Invocation alternatives:** add three separately selectable positive test cases per suite, one for each of `openid4vp://?`, `eu-eaap://?`, and optional `haip-vp://?`, as detailed below. Each generates its own fresh VP request, selects that invocation URI, and checks query/method preservation. Unsupported authorities/schemes and unflagged `openid4vp://present` belong to separately labelled negative cases, not a combined positive case.
4. **Acknowledgement:** validate HTTP 200, optional `redirect_uri`, and absence of the legacy strict `status: "ok"` contract. With a redirect, check the public base path survives (e.g. `/rfc-issuer/verificationStatus?...`) and the wallet follows it. Obtain the presentation outcome through the existing status poll.
5. **Error submission:** a verified request that cannot be fulfilled posts `error`, `error_description`, and exact echoed `state` to its validated `response_uri`. An invalid/unverified JAR must not cause a POST to its claimed destination. Negative cases need observable wallet error/policy evidence, not just a timeout.

The current backend retains an explicit `direct_post` override for compatibility, but these suites must never expose it as a successful CS-02 case or selectable mode. Use only default/explicit `direct_post.jwt` in positive cases. If a normative rejection test discovers that the backend accepts excluded plaintext, report the runtime/profile gap rather than making that case a success. Keep CS-03 compatibility outside these suites; strict wallet encryption failure must not silently downgrade a successful presentation.

### Planned parametric invocation contract

Pass `invocation_scheme=openid4vp`, `invocation_scheme=eu-eaap`, or `invocation_scheme=haip-vp` to generation. Omission defaults to `openid4vp`; unsupported/empty/repeated values return HTTP 400 `invalid_request`. Values contain no colon or slashes. This contract requires the linked backend change to be implemented and deployed before these new cases execute.

For `invocation_scheme=eu-eaap`, the response is:

```json
{
  "sessionId": "<id>",
  "qr": "data:image/PNG;base64,<QR encoding this eu-eaap URI>",
  "deepLink": "eu-eaap://?request_uri=...&client_id=...&request_uri_method=post"
}
```

Both `deepLink` and `qr` must reflect the requested scheme. The suite uses the returned QR directly and verifies its decoded `vpCode` agrees with `deepLink`; it must not select from `deepLinks` or rewrite/re-encode a default QR. A supplemental `deepLinks` field may remain for backward compatibility, but the cases do not depend on it.

Generation creates a VP session; there is no backend endpoint that writes suite XML. Edit those suite files locally. Use a fresh UUID for each independently executed invocation case; preserve encoded query values and the endpoint's advertised retrieval method.

### Retrieval, response and outcome endpoints

- Fetch the URL decoded from `request_uri`, using its advertised method. For POST send form-urlencoded `wallet_nonce=<fresh base64url nonce>`; applicable wallet metadata goes in a JSON-string `wallet_metadata` form field. Assert the signed JAR echoes the POST nonce. GET has no form body. A normal JAR response is `application/oauth-authz-req+jwt`.
- The wallet submits to the JAR's validated `response_uri`, normally `B/direct_post/<id>`, with form-urlencoded `response=<compact JWE>` for encrypted success or `error`, `error_description`, echoed `state` for a protocol error. These are wallet actions; the test script must not fabricate a successful wallet response.
- Poll `GET B/verificationStatus?sessionId=<id>` through the existing receive step. Its HTTP status and JSON `status: "success"`/`"failed"` are **outcome**, distinct from the POST acknowledgement's HTTP 200/optional `redirect_uri`. Retain successful outcome assertions; do not replace all uses of `status` with redirect checks.
- Preserve the existing logs receive step and configured timeout. An intentional rejection needs error/trust evidence; the existing negative template's HTTP `500` / body `fail` is not a general contract for wallet rejection. Confirm adapter mapping and reference `failed` status before writing assertions.
